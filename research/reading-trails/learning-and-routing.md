# Learning from Reading Trails

**Document role:** Reading Trail → research/project routing guide  
**Status:** Developing; AI-assisted; author review pending  
**Updated:** 2026-09-25  
**Canonical method:** [Root Sequence Research Method](../method.md)

Reading Trails are entrances, not endpoints. They can help us discover a question, revise a design, find an existing method, or decide that an attractive idea does not belong in a project.

## Two entrances to the same loop

**Question-led:** encounter a problem → use the [method router](../method-router.md) → discover a field or trail → inspect sources → propose a local change → test and revise.

**Discovery-led:** wander a trail → encounter an unfamiliar distinction, method, or counterexample → ask what it could change → check the source and competing interpretations → route to a bounded inquiry or project → test and revise.

Both return new questions, missing vocabulary, source corrections, and counterexamples to the trails. Neither requires starting with a project, and curiosity does not owe the ecosystem a deliverable.

This page applies the existing method's source, translation, operationalization, and revision steps. It is not a second research method or a claim that RS invented this process.

## Promote a useful distinction, not an entire field

Before adding work to another repository, ask:

1. What did we actually inspect, and what narrow statement does it support?
2. Which live question, assumption, requirement, model, or practice could change?
3. What already exists at the destination? Add to it rather than creating a parallel treatment.
4. What would challenge the proposed transfer, and what is the smallest useful check?
5. Where will its result, rejection, or revision live, and what can safely return here?

A good integration can be a clearer uncertainty label or one new failure case. More prose, more links, and more agreement are not themselves learning. If an idea adds no useful distinction, record that briefly or leave it as a discovery lead.

## Keep evidence and adoption separate

**Evidence status:** discovery lead → specified source portion checked → bounded analysis or observation. Record what remains unread. A landing page, paper abstract, methods section, dataset inspection, and replication are different depths of work.

**Project status:** proposed → reviewed → tested where appropriate → adopted, narrowed, rejected, or deferred. These are not automatic transitions. A documented source can yield an unsuitable design; a merged proposal is not an executed test; a passing software test is not a real-world finding.

Use the destination's existing status vocabulary instead of imposing a new global enum or tracker. Route substantive results through the [research method](../method.md), including competing explanations, competent baselines, and null results.

## Small integration record

Add this information to an existing research register, decision record, scenario, or issue. A separate file is only useful when there is enough substance to maintain.

```text
Entry direction and trail:
Source + date/version + exact portion inspected:
What the source supports / does not support:
Destination and existing question:
Proposed change (or no change) + reason:
Alternative explanation / countercase:
Smallest check + evidence needed:
Result and scope: NOT RUN unless actually executed
Local review/adoption decision:
Return to trail: new question, correction, source, or counterexample
Access and reuse boundary:
```

An AI-generated synthesis remains AI-assisted. It must not be presented as independent corroboration of the sources or of its own proposals.

## Return without duplicating or leaking

Keep claim-level analysis and implementation decisions at their canonical homes. Link back to the source trail for discovery; add a short correction or new doorway here only when it helps another reader. The Wiki can index durable vocabulary and relationships without copying the full research. A paper's claims ledger changes only when the actual argument or evidence changes.

Public branches and pull requests are public. Return only independently public-safe material; private tests, participant details, operational plans, unpublished fiction, and private review links do not become public because they were useful. When a return cannot safely be public, keep it at its private destination rather than inventing a public status claim.

A concrete public first probe lives with the [Commons of Inquiry precedent work](../../incubator/commons-of-inquiry/precedents/reading-trail-probe.md). It is a proposed learning exercise, not a completed pilot or adopted institutional design.
