# Root Sequence Research Method

**Document role:** Canonical cross-project research method  
**Status:** Developing / active, 2026-09-24  
**Scope:** How Root Sequence turns an intuition, pattern, or cross-domain connection into research that can be checked, narrowed, split, or retired.  
**Evidence boundary:** This method draws on established practices including source criticism, comparative method, critical systems thinking, methodological pluralism, preregistration, falsification-oriented testing, and domain-specific research methods. It is a Root Sequence workflow, not a claim of methodological novelty.

## Short version

> **Notice → preserve → decompose → route → source → compare → test → revise → translate → observe → repeat.**

The method is designed for a recurring Root Sequence problem:

> A pattern feels important across several domains before we know whether the similarity is causal, structural, metaphorical, normative, or accidental.

The goal is to **preserve the generative insight without allowing the insight to outrun the evidence**.

---

## 1. Notice the pattern

Start with the thing that feels connected.

Examples:

- "This trauma/adaptation pattern looks like something institutions do."
- "Repairability, exit, and agency seem to share a deeper structure."
- "A system can change not only state but how it changes later."
- "People may be unable to find knowledge because they don't yet know the vocabulary."

Do not require polished academic language at this stage.

Record the intuition before cleaning it up.

### Output

A plain-language observation or question.

### Failure mode

Rejecting an insight because it is not yet technically formulated.

---

## 2. Preserve the raw insight

Capture:

- original wording;
- context that triggered it;
- examples;
- analogies;
- emotional/intuitive significance where relevant;
- immediate connections;
- unresolved contradictions.

Preserving provenance matters because later formalization can accidentally erase what was actually interesting.

### Output

Conversation provenance, Idea Trail, seed note, or research log.

### Failure mode

Replacing the original question with a polished formulation so early that the real question disappears.

---

## 3. Decompose the concept

Before treating a striking phrase as one phenomenon, ask what it contains.

Example:

"agency envelope" decomposed into:

- affordance;
- reachability;
- substantive opportunity;
- knowledge;
- perceived feasibility;
- authorization;
- material support;
- causal control;
- power over conditions;
- value/choice.

"meta-agency" decomposed into:

- self-modification;
- environment modification;
- institutional modification;
- capacity building.

### Output

Distinction table / concept decomposition.

### Failure mode

Inventing a new latent variable that merely bundles several existing concepts.

---

## 4. Route to native disciplines

Ask:

> **Who already studies each mechanism?**

Examples:

| Question | Native methods / literatures |
| --- | --- |
| technical failure/propagation | reliability engineering, SRE, safety engineering |
| constrained reachability | control theory, viability theory |
| substantive human opportunity | capability approach, accessibility/usability |
| contested system boundary | Critical Systems Heuristics |
| multiple problem framings | Soft Systems Methodology |
| organizational governing assumptions | double-loop / organizational learning |
| organizational viability | organizational cybernetics / VSM |
| ecological adaptation | ecological resilience / adaptive management |
| trauma | trauma/stress/clinical/lived-expertise literatures |
| consciousness | neuroscience, philosophy of mind, comparative consciousness |
| information discovery | information science, HCI, exploratory search |

### Rule

> **If a mature field already owns the mechanism, learn its distinctions before creating Root Sequence vocabulary.**

### Failure mode

Cross-domain language replacing domain expertise.

---

## 5. Build the source trail

Distinguish:

- **claim evidence** — supports or constrains a specific factual claim;
- **related work** — shows prior concepts/methods;
- **orientation source** — teaches the vocabulary/field;
- **Reading Trail** — helps humans discover the intellectual neighborhood;
- **historical source** — establishes provenance;
- **counterexample / critique** — challenges the proposed synthesis.

Prefer primary research and authoritative references for consequential claims.

Preserve weird useful websites and archives separately as Reading Trails rather than pretending they prove the claim.

### Failure mode

Bibliography inflation: collecting titles without reading enough to know what they support.

---

## 6. Classify every important statement

Use labels such as:

- **EMPIRICAL / DOMAIN RESULT**
- **MATHEMATICAL / FORMAL RESULT**
- **WORKING DEFINITION**
- **PHILOSOPHICAL ARGUMENT**
- **MODEL / METAPHOR**
- **STRUCTURAL ANALOGY**
- **INTERPRETATION**
- **NORMATIVE COMMITMENT**
- **HYPOTHESIS**
- **SPECULATION**
- **UNKNOWN**

A thought experiment is not an experiment.

A cross-domain resemblance is not evidence of a shared mechanism.

A compelling metaphor is not a causal explanation.

---

## 7. Restore the differences

After finding similar structure, deliberately ask how the cases differ.

For every transfer:

| Dimension | Domain A | Domain B |
| --- | --- | --- |
| state |  |  |
| mechanism |  |  |
| feedback |  |  |
| memory/history |  |  |
| boundary |  |  |
| agency |  |  |
| power |  |  |
| evidence |  |  |
| timescale |  |  |
| normative stakes |  |  |

Possible conclusion:

- same mechanism;
- related mechanism;
- partial structural analogy;
- useful metaphor only;
- misleading resemblance;
- unresolved.

### Failure mode

Everything becoming "the same pattern" because the abstraction is too loose to fail.

---

## 8. Map boundary and power

Before saying a system "works," ask:

- Who defined the purpose?
- Who chose the boundary?
- Who decides?
- Who controls resources?
- Whose knowledge counts?
- Who is affected but not involved?
- Who can appeal, refuse, exit, repair, revise?
- Who bears externalized costs?
- Who can alter the conditions of everybody else's future action?

Use established critical-systems methods when this is central.

### Failure mode

Systems language turning domination into neutral architecture.

---

## 9. Generate competing explanations

Never let the favored synthesis be the only live model.

Record:

- ordinary domain explanation;
- alternative mechanism;
- simpler explanation;
- confound;
- measurement artifact;
- selection effect;
- structural explanation;
- historical explanation.

Ask:

> What would we believe if the exciting synthesis were false?

### Failure mode

The framework explaining everything because nothing else is allowed to explain anything.

---

## 10. Compare against a competent baseline

A Root Sequence method does not earn credit merely because it can describe a case.

Before testing, select the strongest reasonable native baseline.

Examples:

- ordinary competent reliability review;
- STPA;
- capability approach;
- Critical Systems Heuristics;
- accessibility evaluation;
- viability analysis;
- organizational-learning analysis.

Give methods:

- the same evidence;
- the same decision question;
- comparable resources.

Record:

- unique consequential findings;
- duplicate findings;
- false alarms;
- unsupported extrapolation;
- information requests;
- privacy burden;
- analyst burden;
- disagreements.

### Rule

> **Rediscovering a baseline method's central insight is not added value.**

---

## 11. Freeze before testing

When doing a comparison:

1. select the case;
2. explain why it was selected;
3. freeze the evidence packet;
4. freeze method prompts;
5. state conflicts of interest;
6. state the null result;
7. state what would make the framework narrower.

Do this **before** method outputs.

### Failure mode

Editing the method after seeing which case it loses.

---

## 12. Prefer adversarial cases

Do not begin with the example that most beautifully illustrates the theory.

Prefer cases where:

- established methods should perform well;
- the framework could genuinely add nothing;
- the evidence contains ambiguity;
- several interpretations remain possible.

A near-null result is valuable.

### Example

The first T-003 Cloudflare pilots found almost no unique decision-relevant value from Dynamic Coherence beyond competent ordinary incident review.

That result narrowed the framework toward a routing/synthesis role.

This is desired behavior.

---

## 13. Let concepts fail

Allowed outcomes:

- **KEEP** — useful and discriminating;
- **NARROW** — useful in a smaller scope;
- **SPLIT** — one concept was several;
- **ROUTE** — established literature owns the mechanism;
- **RENAME** — terminology collides or misleads;
- **ARCHIVE** — historically useful, not current;
- **RETIRE** — adds no useful distinction.

Do not reward a concept simply for having accumulated documentation.

---

## 14. Translate locally

A shared concept should not be copied wholesale across projects.

Ask:

> What changes in this project's actual design/research problem?

Examples:

- Dynamic Coherence → Coherent Computing: future capability after adaptation.
- Dynamic Coherence → Community Infrastructure: provider/institution dependency and later replaceability.
- Adaptive continuity → Liberated Intelligence: rule-level revision accountability.
- Epistemic discoverability → Legible Systems: discover vocabulary before requiring it.

### Failure mode

Every repo acquiring a near-identical manifesto.

---

## 15. Operationalize

A useful concept should eventually change something inspectable:

- design requirement;
- acceptance case;
- model variable;
- experiment;
- research question;
- documentation structure;
- interface;
- scenario;
- decision process.

If nothing changes except prose, ask whether the concept is doing work.

---

## 16. Observe consequences

After applying the idea:

- what became easier to notice?
- what became harder?
- what did the concept obscure?
- did users/reviewers interpret it consistently?
- did it add burden?
- did it change a decision?
- did it create new lock-in?
- what did the intervention make possible next?

The result becomes new evidence.

---

## 17. Revise visibly

Preserve:

- prior version;
- reason for revision;
- evidence that prompted it;
- what was retained;
- what was rejected.

Do not rewrite history to make current theory appear inevitable.

> **Research itself should exhibit accountable adaptation.**

---

## 18. AI-assisted research rules

AI can be useful for:

- externalizing many simultaneous ideas;
- literature discovery;
- terminology routing;
- source comparison;
- structured extraction;
- counterexample generation;
- drafting distinctions;
- maintaining research maps.

AI must not silently convert:

- plausible wording → established finding;
- source proximity → source support;
- analogy → mechanism;
- thought experiment → data;
- repetition → confidence;
- synthetic review → independent review.

When AI helped generate the framework being tested, disclose the conflict.

An AI grading its own theory is an editorial pilot, not validation.

---

## 19. Research-slop test

Ask:

1. Is the claim falsifiable or at least discriminating?
2. Does the vocabulary correspond to a mechanism, relation, or useful distinction?
3. Could an established term do the job better?
4. Have counterexamples been preserved?
5. Did we compare against competent alternatives?
6. Is evidence attached to the actual claim?
7. Does the synthesis retain domain differences?
8. Would we publish a null result?
9. What would make us retire the concept?
10. Has the concept changed something beyond the prose?

If most answers are no, stop expanding.

## Working principle

> **Connect boldly. Claim cautiously. Route mechanisms to the people and fields that know them best. Build the synthesis so it can survive being wrong.**
