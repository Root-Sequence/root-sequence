# T-003 Editorial Pilot 001 — Method A output

**Method:** competent ordinary incident/system review  
**Status:** FROZEN EDITORIAL OUTPUT  
**Evidence:** frozen Cloudflare June 20, 2024 packet only  
**Maximum findings:** 12  
**Independent validation:** no

## A-01 — Fix the two-condition software defect and make the failure impossible to recur through the same path

**Category:** prevention

**Finding:** The immediate software failure required an unanticipated internal API relationship plus a second cookie-validation function that could disagree with the earlier check. Together they allowed the key generator to call itself indefinitely.

**Packet basis:** The packet reports both conditions and the resulting 100% CPU loop.

**Why it matters:** Either defect remaining can preserve part of the failure path; fixing only the triggering rule would leave latent implementation risk.

**Proposed action:** Unify or make explicit the cookie-validation contract; prevent self-referential key-generator configuration; add tests covering internally generated rate-limit rules and mixed-validity cookie cases.

**Uncertainty / missing evidence:** The packet does not describe existing test coverage, type/interface constraints, or whether similar key-generator composition exists elsewhere.

---

## A-02 — Add execution bounds so one request cannot permanently consume a worker

**Category:** containment

**Finding:** Proper tail-call behavior meant the loop did not necessarily fail through stack exhaustion; a poisoned process could remain alive while consuming a full CPU.

**Packet basis:** The packet reports that a triggering request could leave a request-handling process indefinitely CPU-saturated.

**Why it matters:** A defensive runtime limit would reduce the consequence of an unforeseen logic loop even if a similar defect escaped testing.

**Proposed action:** Add bounded uninterrupted/total execution time or an equivalent watchdog/cancellation mechanism around request processing; test failure behavior when a limit is exceeded.

**Uncertainty / missing evidence:** The packet does not state the latency/cost tradeoffs or which layer can safely enforce a bound.

---

## A-03 — Retire or isolate the legacy rate-limiting implementation

**Category:** prevention / dependency reduction

**Finding:** The affected DDoS path used a legacy rate-limiting implementation while customer-configured rate limits used a newer engine.

**Packet basis:** This distinction is stated in the follow-up actions.

**Why it matters:** Parallel implementations increase the chance that fixes, invariants, and protections diverge.

**Proposed action:** Prioritize migration to the newer/replacement engine or define a bounded compatibility/isolation plan until migration is complete; inventory unique legacy behaviors before removal.

**Uncertainty / missing evidence:** The packet does not establish that the newer engine is immune to analogous bugs or show migration complexity.

---

## A-04 — Strengthen progressive rollout and automatic promotion/stop criteria

**Category:** prevention / blast-radius control

**Finding:** The new DDoS rule was staged in a handful of production data centers and then deployed globally within several hours, before the latent failure was encountered.

**Packet basis:** Deployment began at 14:14, reached all data centers by 17:06, and the first poisoned process appeared at 17:47.

**Why it matters:** Staging provides limited protection if the triggering request does not occur during the observation window or if promotion criteria are not sensitive to the relevant failure.

**Proposed action:** Define explicit canary duration, traffic diversity, health signals, automatic halt criteria, and rapid global rollback for new network-wide mitigation rules; consider progressive exposure by traffic/request class as well as location.

**Uncertainty / missing evidence:** The packet does not provide existing promotion criteria, canary traffic representativeness, or rollback automation.

---

## A-05 — Make traffic shifting aware of pathological work, not only load

**Category:** containment

**Finding:** Unimog and Traffic Manager responded to high CPU by moving traffic, but the moved traffic included requests that could poison additional processes and data centers.

**Packet basis:** The packet explicitly describes this propagation.

**Why it matters:** A normal load-balancing response became a failure amplifier because it treated high CPU as a capacity-location problem rather than distinguishing a workload that reproduced the failure.

**Proposed action:** Add signals or circuit-breaking behavior that can quarantine affected service instances/request classes, suppress propagation of suspected pathological traffic, and distinguish capacity shortage from load generated by a stuck processing path.

**Uncertainty / missing evidence:** The packet does not show whether the triggering request could have been reliably classified during the incident.

---

## A-06 — Harden Traffic Manager as a recovery-critical dependency

**Category:** containment / recovery

**Finding:** Traffic Manager developed a separate latent failure under incident conditions and temporarily stopped issuing routing actions while traffic remained shifted away from recovering locations.

**Packet basis:** The packet reports repeated Traffic Manager exceptions/restarts and two periods without new actions.

**Why it matters:** A system relied upon to reduce impact became partly unavailable during the same event.

**Proposed action:** Test Traffic Manager under degraded/compound conditions; isolate failure modes that halt global action; provide a bounded degraded/manual operating mode or redundant control path; alert specifically on loss of routing-action capability.

**Uncertainty / missing evidence:** The packet does not describe Traffic Manager redundancy, operator override, or control-plane architecture.

---

## A-07 — Improve diagnostics for “high CPU with falling traffic” and per-process poisoning

**Category:** detection

**Finding:** Global high CPU triggered incident declaration, but responders initially considered the concurrent network event; recognizing that the highest-CPU locations had the lowest traffic helped shift the hypothesis.

**Packet basis:** The packet describes the initial correlation hypothesis and later diagnostic observation.

**Why it matters:** Global CPU is sensitive but not specific. Earlier discrimination could reduce time to identify a process-level failure.

**Proposed action:** Alert/visualize per-process saturation, non-terminating request duration, traffic-vs-CPU divergence, recent global rule deployments, and the spatial spread of identical process symptoms.

**Uncertainty / missing evidence:** The packet does not state which of these signals already existed but were hard to access.

---

## A-08 — Explicitly manage concurrent-incident hypothesis separation and responder capacity

**Category:** incident response

**Finding:** Many responders were already working the backbone-congestion incident, and early investigation considered the new CPU problem as potentially correlated.

**Packet basis:** The packet states both conditions.

**Why it matters:** Coincident incidents can create anchoring/correlation assumptions and reduce available investigative capacity.

**Proposed action:** Define a lightweight mechanism to fork incident hypotheses/workstreams, assign independent leads when evidence supports separateness, preserve shared observations, and maintain reserve responder capacity for compound incidents.

**Uncertainty / missing evidence:** The packet does not provide staffing levels, incident-command roles, or whether resource contention materially lengthened recovery.

---

## A-09 — Automate selective recovery without creating restart storms

**Category:** recovery

**Finding:** Repeated restarts recovered poisoned processes and were used globally while the trigger was being found.

**Packet basis:** The packet reports sample validation followed by broader and repeated restarts.

**Why it matters:** Restarting was useful, but broad repeated recovery actions can themselves create load, obscure diagnosis, or interact with traffic shifting.

**Proposed action:** Define health-based selective recycling/quarantine with rate limits, verify capacity before broad restart waves, and preserve diagnostics from poisoned processes before termination where feasible.

**Uncertainty / missing evidence:** The packet does not report negative effects from the restarts; this is a precautionary inference.

---

## A-10 — Test compound failure and remaining-capacity assumptions

**Category:** resilience / verification

**Finding:** Poisoning reduced healthy capacity across regions while Traffic Manager's safety limits constrained further movement and Traffic Manager itself experienced a fault.

**Packet basis:** The packet reports reduced healthy capacity, safety limits, destination scarcity, and Traffic Manager interruption.

**Why it matters:** Controls designed for one degraded condition may behave differently when compute loss, traffic movement, and control-system degradation coincide.

**Proposed action:** Add simulations/load tests for correlated capacity loss plus routing-control degradation; verify that safety limits fail safely and that enough capacity/control remains for recovery.

**Uncertainty / missing evidence:** The packet does not provide capacity margins or prior compound-failure tests.

---

## A-11 — Require post-remediation verification, not only remediation intent

**Category:** verification

**Finding:** The postmortem lists design and process changes, but the packet contains no evidence that they were later implemented or reduced risk.

**Packet basis:** Implementation/effectiveness of remediations is explicitly unavailable.

**Why it matters:** A postmortem action list is not evidence that risk changed.

**Proposed action:** Track each action to implementation, test, owner, completion evidence, and recurrence/leading indicator; later exercise the triggering conditions or a safe equivalent.

**Uncertainty / missing evidence:** The packet intentionally ends before later verification.

## A-12 — Obtain missing architecture and rollout evidence before prioritizing expensive redesign

**Category:** evidence request

**Finding:** Several major recommendations depend on facts the packet does not contain.

**Packet basis:** Explicit unknowns include full architecture/dependency graph, test coverage, rollout criteria, monitoring thresholds, incident command, remediation cost, and independent verification.

**Why it matters:** Without these, reviewers can identify risk themes but cannot responsibly rank migration, redundancy, monitoring, staffing, and rollout changes by cost/effect.

**Proposed action:** Before final prioritization, request: dependency/control diagram; test and deployment gates; rollback mechanism; Traffic Manager redundancy/manual controls; relevant SLO/capacity margins; incident-role timeline; and implementation status of follow-ups.

**Uncertainty / missing evidence:** This finding is itself a request for missing evidence.

## Method A summary

The ordinary review identifies a technically conventional set of priorities:

1. remove the immediate software defect;
2. bound runaway request execution;
3. reduce legacy divergence;
4. improve staged rollout;
5. prevent load-balancing from propagating pathological work;
6. harden the recovery/control system;
7. improve diagnostics;
8. handle concurrent incidents explicitly;
9. make recovery selective;
10. test compound degradation;
11. verify remediation;
12. gather missing evidence before costly redesign.

No claim is made that these are exhaustive or independently validated.
